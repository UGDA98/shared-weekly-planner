## Global constraints (apply to every task)

1. **Never touch a real board.** All testing uses a disposable scratch board created via `action:'createBoard'` and deleted via `action:'deleteBoard'` (the scratchpad `api.mjs` helper follows the 302 manually and retries transient `auth_required`/interstitial responses — Watch Out #15/#18). Always load the live app with an explicit `?board=<scratch-id>` from the first request (Watch Out #23). Confirm `listBoards` shows only real boards after cleanup.
2. **Deploy ordering (NOTES.md "Deploy ordering"):** any backend change that a frontend change depends on must be **deployed and verified on a scratch board before** the dependent frontend ships. Backend deploys never touch stored data; the only risk is manual API calls during debugging.
3. **FedCM cannot be automated** (Watch Out #20). Any step needing a *real signed-in Google session* must be run by the owner in her own browser, or on the owner's already-signed-in Chrome (available this engagement). State this per item.
4. **No severity downgrades** without quoting the finding's cited source lines first (none are downgraded in this plan).
5. **REQUIRE_AUTH decision (owner-approved):** close the `setScriptConfig`/`setAccess` `auth==='plain'` gap **first**, audit the `Log` tab for suspicious `Auth:'plain'` privileged rows, **then** flip `REQUIRE_AUTH` to `'true'`. Flipping alone does not undo a config change already made during the grace period, so the code gap must close before the flip is meaningful.
6. **PWA approach (owner-approved):** in-page version-check + reload banner. **No service worker** (keeps NOTES.md's no-SW decision intact).
7. Commit to `main` after each verified item (work happens directly on `main`; frontend is the only git repo). Update `NOTES.md` in the same commit as the change it documents.

## Batch 1 — Critical security (backend-first)

Order within batch: **B1.1 → B1.2 → deploy+verify backend → B1.3 (frontend XSS, independent) → B1.4 (Log audit) → B1.5 (flip).**

- **B1.1 — Reject `auth==='plain'` on privileged mutations (closes the grace-period backdoor, finding #2).**
  `backend-apps-script/קוד.js`. In `setScriptConfigForClient` (`:243`), `setAccessForClient` (`:923`ish, forbidden log at `:930`), `removeAccessForClient` (`:956`), `setDefaultRoleForClient` (`:983`): after the existing role check, add `if (auth !== 'google') { logEvent(callerEmail, '<action>', board, 'plain_denied', ..., auth); return { ok:false, error:'auth_required' }; }`. The `auth` value already threads in from `resolveIdentity` via `doPost`. Rationale: these four are the account-takeover-relevant writes; plain-email callers must never reach them even during the grace period.
  **Size:** small (4 guard clauses, one helper). **Deps:** none. **Verify:** scratch board — POST `setScriptConfig`/`setAccess` with a plain `email` param (no session) → expect `auth_required`; repeat with the owner's real session → expect success. Also confirm a normal plain-email `saveBoard`/`getBoard` still works (grace period otherwise intact).

- **B1.2 — Formula/CSV-injection guard on all user-controlled cell writes (finding #5).**
  `backend-apps-script/קוד.js`. Add a `function safeCell(v){ v = (v==null?'':String(v)); return /^[=+\-@\t\r]/.test(v) ? "'" + v : v; }` and route every user-controlled write through it: board `Name` (`createBoardRow`, `renameBoardRow:1155`), `Email`/`targetEmail` (`addConfigRow`, `setAccess`), and `logEvent`'s `Board`/`Details`/`note` and the `UserAgent` field (`appendRowByHeader` call sites — simplest to apply inside `appendRowByHeader` for the Log/Sessions/Config sheets, and explicitly at the two `setValue` rename/name sites). Also cap board-name length (~80 chars, strip `\n\r`) and validate `targetEmail` against a basic email regex before storing.
  **Size:** small–medium (one helper + ~6 call sites). **Deps:** none. **Verify:** scratch board — `createBoard` with name `=IMAGE("x")`, `saveBoard` on a bogus id with `board:'=1+1'`, then read the `Boards`/`Log` sheets (owner opens the Sheet, or read the raw cell via a temporary read action) → confirm the leading `'` is present and Google shows the literal text, not a formula. Delete scratch board.

- **Deploy gate:** `clasp push` → `clasp version "v18: reject plain-auth on privileged writes + formula-injection guard"` → `clasp deploy --deploymentId AKfycbx…UgCdwVXCkUU --versionNumber <n>`. Re-run B1.1/B1.2 scratch checks against the **live** deployment before proceeding. (No dependent frontend change here — these are backend-only hardening.)

- **B1.3 — Fix stored XSS in the summary header (finding #1). Frontend, independent of the backend deploy.**
  `frontend/index.html:2830`. Replace the `head.innerHTML = (icon||'') + '<span>'+name+'</span>...' ` string-concat with DOM construction: keep `icon` as-is (it's a trusted SVG constant), but create the name `<span>` via `document.createElement('span')` + `.textContent = name`, and the count span likewise. (Mirror the `renderSummaryRow`/`renderTaskRow` pattern that already uses `textContent`.) Grep for sibling risk: `index.html:3014` (pool header) uses a static string — safe, no change; confirm no other `*.innerHTML =` interpolates a user name (audit already checked — this is the only one).
  **Size:** ~1 line replaced by ~4 lines (one focused edit). **Deps:** none. **Verify:** live browser on a scratch board — add a person named `<img src=x onerror="window.__xss=1">` via the person picker, switch the summary to "group by person," confirm `window.__xss` stays `undefined` and the literal text renders. Needs a real session (person add is an editor action) OR reproduce by seeding `appState` if a test hook is available.

- **B1.4 — Audit the `Log` tab for grace-period abuse (operational, no code).**
  Query `getActivity` (or open the `Log` sheet) and scan for `Auth:'plain'` rows on `setScriptConfig`/`setAccess`/`setDefaultRole`, and any unexpected `Config` editor rows on `board-1`. **Size:** 15 min, owner + executor. **Deps:** B1.1 deployed (so no *new* abuse can land during the audit). **Verify:** documented "clean" result, or a list of rows to investigate.

- **B1.5 — Flip `REQUIRE_AUTH` to `'true'`.**
  Via `setScriptConfig` (now plain-denied, so run it from the owner's real session) or `adminSetRequireAuth(true)` in the Apps Script editor. **Size:** 5 min. **Deps:** B1.1 live + B1.4 clean + confirmation (via `Log`) that every active user has at least one `Auth:'google'` login. **Verify:** a plain-email API call now returns `auth_required`; the owner's own signed-in session still works. **Note:** this ends the grace period — coordinate timing so no staff member has an unsigned open tab mid-task.

## Batch 4 — PWA staleness (owner-approved: version-check banner, no SW)

- **B4.1 — In-page version check + reload banner (finding #8 / P1).**
  Add a build/version marker the page carries and can compare against the server. Simplest for a no-build repo: a `frontend/version.txt` containing a monotonic string (date+counter, bumped every deploy), and a `<meta name="app-version" content="…">` in `index.html` set to the same value at deploy time (a one-line pre-push checklist step, documented in NOTES.md). In the JS: every N poll ticks (e.g. every 5th `refreshFromServer`, ~100s), `fetch('version.txt?t='+Date.now(), {cache:'no-store'})`; if the fetched value ≠ the loaded `<meta>` value, show a non-blocking, dismissible banner ("גרסה חדשה זמינה — הקישו לרענון") whose button calls `location.reload()`. **Do not auto-reload** (would risk an unsaved mid-edit); prompt only. **Size:** medium (banner UI + poll hook + the deploy-time version bump convention). **Deps:** none (frontend-only; `version.txt` served by Pages like any file). **Verify:** live — load the app, bump `version.txt` on the server, wait one check interval, confirm the banner appears and reload picks up the new version. Confirm no banner when versions match. Test in a real standalone PWA window on a phone if possible (owner has a device — the whole point is the standalone case), else note it as a manual owner check.
  **Sub-note:** because this is the fix for a *standalone* PWA that can't be manually refreshed, the one end-to-end check that fully closes it needs the owner's phone (add-to-home-screen window) — flag explicitly, same caveat class as the original PWA-icon check (Watch Out #27).
