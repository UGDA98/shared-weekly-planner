**Data model (multi-board, schema-less)**: Google Sheet with tabs `Boards` (BoardId/Name/DefaultRole/CreatedBy/CreatedAt/**Type**/State-JSON, **plus `State2`…`StateN` chunk columns created on demand**), `Config` (Board/Email/Role, per-board access control), `Sessions`, `Log` (both above). Each board's entire app state is one JSON blob that round-trips as-is through `saveBoard`/`getBoard`/`listBoards`/`createBoard`/`renameBoard`/`deleteBoard` — the backend doesn't understand the shape, just stores/returns it. `Boards.Type` (`planner`/blank or `notes`) selects the board type; `createBoard`/`listBoards`/`getBoard` accept/return it and `defaultBoardState(type)` branches on it (backend, v11+). The frontend picks the type in the new-board modal and branches its entire render on `currentBoardType` — see "Notes boards" below.

**Notes boards** (second board type, added this session): a Notion-style gallery of pages, each an arbitrarily nested outline. Selected via a type-choice card in the new-board modal (`.modal-type-choice`); `currentBoardType` ('planner' | 'notes') drives `renderAll()` to branch between the week board and `renderNotes()` entirely — no shared rendering code between the two types beyond `showUndoToast`/`showConfirmModal`/`persistState`/`stripHtmlPreview`/`relTime`, which are the app's general-purpose primitives already used by the planner side. Shape: `appState = { kind:'notes', pages:[Page] }`, `Page = { id, title, createdAt, updatedAt, blocks:[Block] }`, `Block = { id, html, style:'p'|'h1'|'h2', collapsed, children:[Block] }`. `html` is restricted to `b/i/u/s/br` with no attributes (`sanitizeInline()`, ~[index.html:4340](index.html#L4340)) — enforced on every commit **and** re-applied on every load (`sanitizeNotesState()`) as defense against a write from anything other than this client, since the backend still treats the whole blob as opaque. Collapse state (`Block.collapsed`) is stored in the blob, not per-user `localStorage` like `makeCollapsible` — deliberately, since a collapsed section is content the gallery preview also needs to reflect (see Decisions). No drag-and-drop: all structural editing (indent/outdent/reorder/split/merge) is keyboard shortcuts or a touch toolbar, matching the existing "click-based, not drag-based" pattern for day-assignment (Decisions, `openDayPicker`).

**State chunking (added 2026-09-09)**: a Sheets cell holds max 50,000 characters and `appState.weeks` is never pruned, so the blob outgrows one cell within months of normal use. `saveBoardStateRaw` splits the JSON into ≤45,000-char chunks across `State`, `State2`, … (`ensureStateColumns` appends missing header cells; `stateColIndexes` resolves them), and `getBoardState` concatenates them back. Over `MAX_STATE_CHUNKS` (12, ≈540k chars) it writes **nothing** and returns `state_too_large` rather than corrupting the board with a partial write.

**Day model**: days are `sun, mon, tue, wed, thu, fri, sat` (`DAY_DEFS`). Friday and Saturday were merged into one `weekend` bucket until 2026-09-09 — see Decisions and Watch Out #12.

**Frontend data flow / sync**: poll server every 20s (`POLL_MS`, ~[index.html:702](index.html#L702)) via `refreshFromServer()` (~[index.html:803](index.html#L803)); local edits save to `localStorage` immediately + debounce 600ms before POSTing to server (`persistState`/`pushState`, ~[index.html:752](index.html#L752)/[769](index.html#L769)); immediate flush via `navigator.sendBeacon` on `visibilitychange`/`pagehide`; one-step-back backup always kept in `localStorage` with a "restore from last backup" button in the admin menu.

**Board switching**: `?board=<id>` URL param (read in `resolveInitialBoardId()`, ~[index.html:876](index.html#L876)) takes priority over the last-used board cached in `localStorage`; falls back to `LEGACY_BOARD_ID`. `switchToBoard()` (~[index.html:1149](index.html#L1149)) handles the actual swap.

**Deployment behavior**: frontend push → live in ~1-2 min, but GitHub Pages serves with `max-age=600` (~10 min cache) — a stale-looking page right after push is usually cache, not a bug; hard-refresh or wait.

**Deploy step — bump the app version (REQUIRED on every frontend deploy, added Batch 4 / 2026-09-17).** Installed standalone PWA windows have no reload affordance, so they detect a new deploy by comparing the `<meta name="app-version">` baked into their loaded page against `version.txt` (fetched every 100s on its own timer and whenever the app returns to the foreground — independent of sign-in, since the data poll only starts after sign-in); a mismatch shows a "רענון" banner. **Both must be stamped to the same new value before you push**, or the banner never fires (fails safe — no false reloads, but also no notice). One-liner (run in `frontend/` before committing):
```
V=$(date -u +%Y%m%d-%H%M); printf '%s\n' "$V" > version.txt; sed -i '' "s/name=\"app-version\" content=\"[^\"]*\"/name=\"app-version\" content=\"$V\"/" index.html
```
(GNU `sed`: drop the `''` after `-i`.) No service worker — this is the deliberately-lightweight alternative (see Decisions "PWA manifest with no service worker"). The literal "banner appears in a real installed PWA after a deploy" can only be confirmed on an actual device (like the icon check, Watch Out #27).

### Reusable patterns (use these, don't build parallel mechanisms)

- **Collapse**: any new collapsible UI → use `makeCollapsible`.
- **Drag**: `setupDrag` is the only drag API in the file (`opts.dropzone` for cross-container, `opts.threshold` when the handle overlaps another interactive element like a checkbox).
- **Person/topic tagging**: `makeMetaChip(icon, filled)` + `openPicker(...)`.
- **Destructive row actions**: any new delete affordance → call `showUndoToast(message, onUndo)` instead of `confirm()`/a modal — matches the pattern already used for tasks/events/pool/summary-row deletes (see Decisions).

## Decisions

| Decision | Why | Alternative considered & why rejected |
|---|---|---|
| Single self-contained `index.html`, no build step | Simplicity for a small, single-page tool; easy to deploy straight to GitHub Pages | — |
| Google Sheets (via Apps Script) as the data store, not a real database | Keeps existing org data location, avoids new infra | An earlier, now-abandoned early plan considered calling the Sheets API directly from the frontend — rejected in favor of an Apps Script Web App middle layer for access control per board (`Config` tab) |
| Schema-less JSON blob per board, not normalized rows | Fast to iterate on frontend data shape without backend migrations; backend doesn't need to understand the app's structure | — |
